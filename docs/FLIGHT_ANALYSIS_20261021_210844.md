时间线与“LIO 约束中断后继续惯性外推并漂移”一致；**LIO 为什么中断仍未定论**。

## 3. 为什么不是单纯 rosbag 或 RViz 的坐标变换

- 离线使用 `rosbag.Bag.read_messages()` 直接读取位置字段，不经过 RViz 或 TF，EKF 的 z 已到 10.464。
- 本包 `/Odometry` 连接发布者为 `/laserMapping`，EKF 为 `/ekf`，没有记录到这两路的额外回放发布者。
  这不证明用户当前播放环境没有同名发布冲突；回放仍须使用[隔离 master](ROSBAG_RECORD_REPLAY.md)。
- LIO 存在的 143 组配对样本中，位置差 p95 约 0.025 米、最大约 0.037 米；
  **这个配对统计不覆盖 LIO 停止后的 11.434 秒**，不能以配对误差小认定全程 EKF 正常。
- 缺少 `camera_init ↔ world` 的真实 TF 仍是接口问题，但缺 TF 本身不能解释已存储的位置字段为何上升。
  不应加虚假的单位变换“修好”这个包；本次也未排除 IMU 方向、外参或时间轴错误对漂移的影响。
- `/path` 是 FAST-LIO 的累计历史路径，本包第一条 Path 已包含 65 个历史点；不是从本次录包开始的 EKF 轨迹。
  回看 EKF 要选择 `/ekf/ekf_odom`，不要混同累计 `/path` 或预测输出 `/ekf/ahead_ekf_odom`。
- 本包没有 `/goal` 和 `/setpoints_cmd` 消息；不能把本次上漂解释为规划器已发出持续上升轨迹。

## 4. 控制链上暴露出的保护缺口

EKF IMU 回调在初始化后继续 `system_pub()`；当前 PX4Ctrl 的 `odom_is_received()` 主要检查
EKF 消息接收时间。只要 EKF 高频发布，接收超时检查不会识别“更上游 LIO 已停止约束”。
因此需要区分 **消息新鲜**、**LIO 观测连续**、**估计可信**，三者不是同一件事。
本次只增强离线诊断，没有改动飞行控制器或加自动模式切换，避免未经验证的保护动作。

同次启动的 `~/gcs_ws/log/fastlio2_ekf_20261021_210719/fast_lio_rviz.log` 在
21:09:19.536 起出现 `No Effective Points!`、`Too few input point cloud!`、`No point, skip this scan!`。
这些日志出现在本包结束后约 0.365 秒，提示感知处理异常，但**不能当成第 14.34 秒中断的已证根因**。
包内没有原始 `/livox/lidar`，不足以进一步区分驱动断流、同步等待、处理阻塞或有效点退化。

## 5. 下一步只做地面排查

1. 暂停自动起飞，地面锁桨检查；不要为了复现而直接再次起飞，也不要空中重启感知节点。
2. 同时检查 `/Odometry`、`/cloud_registered` 与 `/ekf/ekf_odom`，不要只盯 EKF 频率。

   原始点云增大磁盘负载，先确认空间和负载。只记录当前处理结果无法定位输入断流的位置。
4. 核对 LiDAR 与 PX4 IMU 的时间戳连续性和偏移、FAST-LIO 有效点数量、进程负载/磁盘阻塞、传感器供电/网络。
   机体振动、外参与坐标方向仍需检查，但不能先认定单一坐标翻转就是根因。
5. 后续保护应监控独立的 LIO 观测年龄及估计健康，而不只是 EKF 输出频率；必须先地面/离线验证。
