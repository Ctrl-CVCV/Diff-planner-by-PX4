# 2026-10-20：发出 0.5m 航点后仍悬停的录包分析

## 1. 结论

**这一次目标确实送达规划器，PX4Ctrl 也短暂进入了指令控制；但规划器连续碰撞判定失败，
随后发出的不是前进轨迹，而是当前位置的应急停留轨迹。**
因此不能把问题归因于“脚本没发目标”或“PX4Ctrl 拒绝执行已有前进指令”。
本次主要阻塞发生在规划器的占据/碰撞判断与轨迹生成环节。
至于占据来自真实障碍、膨胀、地面/机身点云、定位与点云坐标不一致，还是其他地图问题，
**当前 bag 缺少地图与相关运行参数，不能进一步定责，不能直接断言膨胀距离过大。**

这里的 “crash” 是优化器在地图中找不到前方自由约束点时打印的错误文案，
**不能当成飞机真的发生碰撞的证明**。
目标并未被报告为越过安全高度边界，而是收到后参与规划、随后碰撞判定失败。
正常的全局参考线也不能证明局部避障轨迹生成成功。

## 5. 目标、指令、实际位置对比

目标发送附近最近的 EKF 样本为：

```text
实际估计位置：(-1.079197, 1.044437, 0.856357)
发送目标位置：(-0.579326, 1.044881, 0.856567)
差值约为：   (+0.499872, +0.000444, +0.000210) m
```

偏移确实是 world +X 约 0.5m；不是因为目标重复设置成了当前点。
目标采用发送前的 EKF 样本，最近样本相隔约 2ms，因此差值不是严格的 `(0.5,0,0)`。

但全部 200 条 `/setpoints_cmd` 都是：

```text
position = (-1.072321, 1.042372, 0.855296)
velocity = (0, 0, 0)
acceleration = (0, 0, 0)
jerk = (0, 0, 0)
trajectory_id = 1
trajectory_flag = 1
```

它们持续约 1.990 秒，指令位置完全相同，离发目标时的实际位置仅约 0.0073m，
而不是指向 0.5m 外的目标。目标后约 3 秒的 EKF 位置为
`(-1.074675, 1.027829, 0.854533)`，离目标仍约 0.496m，符合原地悬停而非前进。

对应源码中，`DiffPlannerManager::EmergencyStop()` 用同一个 `stop_pos` 作为起点和终点，
速度/加速度为零，生成两段各 1 秒的轨迹；`callEmergencyStop()` 把它发给轨迹服务器。
这与本次约 2 秒的常值指令高度一致。由于没录多项式消息，不能直接展示当时的多项式系数，
但日志、200 条实际指令和本地实现共同支持“应急原地停留”的判断。

`trajectory_flag=1`、新指令出现、`CMD_CTRL(3)` 都不区分“朝目标前进”与“应急停留”。
当前顺序脚本的成功提示只验证了链路交接，不验证可达性/运动轨迹或到点。
不要因此重复给目标、跳过碰撞检查、放大速度或取消膨胀。

## 6. 下一步优先排查

1. 在地面检查注册点云与 EKF 的数值坐标、原点、方向、时间关系；frame_id 相似或 RViz 看着重合不够。
2. 检查预计悬停高度附近，起点/目标是否被膨胀占据；追踪对应的未膨胀点云到底是地面、机体、墙面还是其他真实物体。
3. 确认不是坐标错位、机体自反射、地面点、陈旧占据残留或缺失数据；不能先假定“没有实际障碍”。
4. 保存本轮规划器参数、原始/膨胀地图、注册点云、规划轨迹与心跳，再讨论膨胀和高度带。
5. 同时处理电池告警，再考虑任何实飞。

本次飞行期间 `/px4ctrl` 还反复报告 `Dangerous!`，例如
`1792503958.799816` 时 `voltage=22.274, percentage=0.000`。
这不是本次“为什么没有前进指令”的直接证据，但属于独立安全问题。
电量随后回升，不能仅凭这个百分比断言电池真的耗尽，也不能把告警直接忽略；
需在地面校核电池状态、负载压降与 PX4 电量估计/阈值。
