## 1. 先理解“接管”

实际控制链始终是：

```text
Diff-Planner → /setpoints_cmd → PX4Ctrl → MAVROS → PX4
```

并不是让 Diff-Planner 直接给电机下指令。顺序脚本只做：

1. 检查现有节点、参数、话题、频率、遥控器与地面状态；
2. 发送一次 `/px4ctrl/takeoff_land` 起飞请求；
3. 等待 `/px4ctrl/state` 确实进入 `AUTO_HOVER(2)`；
4. 连续稳定悬停至少3秒；
5. 在稳定悬停点的基础上，向 `/goal` 发送一个短距离目标；
6. 确认新的 `/setpoints_cmd` 与 `CMD_CTRL(3)`，继续观察从发目标起的真实水平位移；
7. 发目标后 3 秒内最大水平位移不足 0.05m 时，在遥控/定位/飞控状态有效的前提下单次请求 LAND，并等待 `AUTO_LAND(5)` 确认。

脚本不会启动/终止控制节点，不调用解锁或模式服务，不重复起飞、不直接解锁或强制停桨；只在目标后无位移保护条件满足时请求 PX4Ctrl 降落。**但当前 PX4Ctrl 的 `enable_auto_arm=true` 会使起飞请求间接触发自动解锁。**

## 2. 当前不应跳过的前提

此前反馈的“空旷处有方块、障碍物处空白”必须先确认解决。不要为了让脚本通过而直接勾选地图确认选项。

至少验证：

- 原始点云和 EKF 数值坐标对齐；
- 未膨胀地图正确对应实际障碍；
- 膨胀地图中，起点、目标点以及预期飞行高度有足够自由空间；
- 没有因地面向上膨胀而把飞行高度占满；
- 目标方向无人、无硬墙，遥控器能及时接管。

`--map-verified` 仅表示操作者人工确认，不是自动碰撞检测。脚本只检查地图消息新鲜度；当前发布地图存在高度和前向裁剪，不能用它证明整条航线自由。

## 4. 启动顺序

终端1，已有感知与融合脚本：

```bash
source ~/gcs_ws/devel/setup.bash
bash ~/gcs_ws/src/livox_ros_driver2/scripts/start_fastlio2_ekf.sh
```

终端2，规划器与轨迹服务器：

```bash
source ~/gcs_ws/devel/setup.bash
roslaunch diff_planner run_exp_single_lio.launch
```

**在启动终端3之前**，先确认飞机落地、未解锁，将遥控器准备到你已经验证过的中油门自动起飞组合：
CH1～CH4 居中，CH5、CH6 高位，准备后保持开关不动。不要先启动控制器再从低位拨到高位。

终端3，控制器：

```bash
source ~/gcs_ws/devel/setup.bash
roslaunch px4ctrl run_ctrl_lio.launch
```

**本次不要启动 multipoint 节点，也不要提前点击 RViz 目标。** 这样既避免多个目标源，又避免起飞前 `/setpoints_cmd` 已经持续输出。若本轮已发过规划目标，轨迹服务器可能继续输出终点指令，需要在地面、未解锁且确认安全时重启规划器启动流程；不要在空中重启控制链。

保持前面准备好的遥控器组合。当前源码要求：

- CH1~CH4 全部居中，油门也居中；脚本按1500±125检查，对应源码死区；
- CH5 > 1750，CH6 > 1750；
- RC数据持续有效；
- 飞机落地、未解锁，PX4Ctrl处于 `MANUAL_CTRL(1)`。

这几个通道是本地 `input.cpp` 的实际解释，并不等同于QGC中的飞行模式名称。脚本不修改或绕过飞控的解锁条件、kill-switch、模式映射。

`AUTO_HOVER(2)` 是控制器内部状态，不证明飞机已经离地。控制器启动后 CH5 的低→高边沿
也可能在地面触发 `MANUAL_CTRL(1) → AUTO_HOVER(2)`，此时即使最终键位正确，起飞脚本仍会拒绝。
第一帧 RC 位置作为初始值，所以应先准备好开关再启动控制器。
若已进入状态2，仅在确认落地、`/mavros/state.armed=false`、`landed_state=1` 后，
停止并按上述顺序重新启动 PX4Ctrl，再运行不带 `--execute` 的预检。
不要在空中重启控制链、反复发起飞命令，或把脚本放宽为允许状态2再次起飞。

## 5. 先只检查，不起飞

终端4：

```bash
source ~/gcs_ws/devel/setup.bash
python3 ~/gcs_ws/src/livox_ros_driver2/scripts/takeoff_then_diff_planner.py
```

默认只检查，没有任何起飞或目标发布。脚本会检查：

- `/px4ctrl/state` 是否存在且为1；
- PX4是否连接、未解锁且报告在地面；
- EKF、IMU、RC消息是否新鲜，EKF/IMU时间戳是否合理；
- EKF、IMU接收频率是否达到100Hz；
- 当前静止速度是否不超过0.1m/s；
- 起飞前至少2秒没有收到 `/setpoints_cmd`；
- `/setpoints_cmd` 唯一发布者是否为当前轨迹服务器；
- 是否没有其他 `/goal` 发布者；
- 规划器最大速度是否不超过0.3m/s；
- 规划器高度边界已启用，预期起飞高度与上下边界至少留0.2m余量。

默认节点名固定为本工作空间的 `/px4ctrl`、`/drone_0_diff_planner_node`、`/drone_0_traj_server`。如果使用了命名空间或修改节点名，应先修改脚本常量与检查逻辑，不要盲目删除安全检查。

## 6. 第一次建议：只验证起飞与悬停

仅在地图及场地确认安全后：

```bash
python3 ~/gcs_ws/src/livox_ros_driver2/scripts/takeoff_then_diff_planner.py \
  --execute --map-verified --takeoff-only
```

终端会要求输入 `TAKEOFF`。输入后会再次检查条件，然后只发送一次起飞请求。

此模式确认连续稳定悬停后退出，不发送规划目标；降落和后续接管由飞手负责。

## 7. 完整流程：起飞、稳定悬停、发送短距离目标

应从新一轮安全的地面未解锁状态开始，不要在上一轮已悬停时重复运行。

```bash
python3 ~/gcs_ws/src/livox_ros_driver2/scripts/takeoff_then_diff_planner.py \
  --execute --map-verified \
  --goal-dx 0.5 --goal-dy 0.0
```

输入 `TAKEOFF` 后，脚本将：

```text
一次起飞请求
    ↓
AUTO_TAKEOFF(4)
    ↓
AUTO_HOVER(2)
    ↓
连续3秒位置/速度稳定
    ↓
/goal = 当前悬停位置 + (0.5, 0.0, 0.0)
    ↓
确认新轨迹指令与CMD_CTRL(3)
    ↓
继续监护到发目标后3秒：最大水平位移不足5cm则请求LAND
```

**最后一步只验证链路交接，不验证已经生成朝目标运动的轨迹。**
本次 21:45 录包中，规划器因碰撞判定连续失败，随后输出应急原地停留轨迹，
也让控制器进入了状态3并满足脚本的交接条件。因此必须同时检查规划错误、指令位置/速度和实际位移。

**偏移使用世界/EKF坐标轴，不是机头前方！** 若机头没有对齐world +X，`--goal-dx 0.5` 不一定让飞机沿机头方向前进。

目标Z保持交接时实测悬停高度。起飞相对高度从运行时参数 `/px4ctrl/auto_takeoff_land/takeoff_height` 读取，脚本不修改它。

如果地面EKF z约为0，当前起飞高度0.8m、虚拟天花板1.2m，预期目标高度约为0.8m。脚本不会自动把天花板改成1.2m，应先在launch中设置并重启规划器。

## 8. 稳定悬停判断

脚本同时要求：

- 控制器真实状态为 `AUTO_HOVER(2)`；
- 飞控已解锁且处于 `OFFBOARD`；
- 与起飞点的XY距离不超过0.25m；
- 相对预期起飞高度误差不超过0.12m；
- EKF速度模长不超过0.12m/s；
- 连续满足至少3秒，中断会重新计时。

因此不是简单 `sleep 10` 后盲目发目标。

### 起飞状态回报的异步确认

2026-10-20 的录包 `flight_logs/20261020_211622/takeoff.bag` 确认过一次时序误判：

- `/px4ctrl/state` 在 ROS 时间 `1792502351.491952` 先发布 `AUTO_TAKEOFF(4)`；
- 旧脚本在 `1792502351.530387` 因仍看到未解锁的 MAVROS 状态而退出；
- `/mavros/state` 到 `1792502352.153621` 才回报 `armed=true, mode=OFFBOARD`；
- 控制器随后正常进入 `AUTO_HOVER(2)`，但顺序脚本已退出，因此不会再发送 `/goal`。

PX4Ctrl 的模式/解锁服务响应与 `/mavros/state`、`/px4ctrl/state` 是不同的回报链，
不能要求首次看到 `AUTO_TAKEOFF` 的同一轮采样就同时看到已更新的 MAVROS 状态。
新版脚本只在首次 `AUTO_TAKEOFF` 且尚未确认飞控状态时，最多等待 2 秒。
此等待仅限 EKF 实测距起飞点不超过 0.1m、速度不超过 0.1m/s；
保留 RC、连接、消息时效和提前轨迹指令检查，不发布规划目标，也不重复请求起飞。

本次录包中 `extended_state.landed_state` 在起飞请求后约 0.17 秒就变为离地，
但 EKF 在之后约 1 秒内仍仅变化数毫米，因此不能再把这个分类作为等待中的强制地面条件。
起飞前仍要求 `ON_GROUND`；确认窗口内以三维位移、速度和 2 秒截止时间约束，
该窗口短于当前 PX4Ctrl 源码中的 3 秒电机预转阶段。若修改控制器启动时序，需重新验证此假设。

一旦确认 `armed+OFFBOARD`，后续失锁或退出 OFFBOARD 仍立即终止顺序流程；
若已进入 `AUTO_HOVER` 仍未满足飞控状态，也立即终止。超时、离地或移动时不会继续等待。
连续稳定悬停计时仍要求实际 `AUTO_HOVER+armed+OFFBOARD`，不会把起飞确认等待算作悬停。
终端会打印控制器状态、armed 和 mode 的变化，便于区分状态回报延迟与实际掉模式。

该修正只解决本次目标交接被提前中断的问题，不代表地图、轨迹可达性或实飞安全已验证。

## 9. 停止脚本不等于停止飞机

**非常重要：**

- `Ctrl-C` 只停止这个顺序脚本；
- 已发送的起飞请求不会因此撤回；
- 已发送的目标不会因此撤回；
- Diff-Planner和轨迹服务器可能继续输出轨迹；
- 正常结束仅说明初始位移/交接检查完成，或已确认 AUTO_LAND；不代表已到点或已落地；
- 超时/报错后，飞手必须观察飞机状态并使用已验证的RC接管流程。

不要在空中通过杀掉MAVROS、EKF、PX4Ctrl或直接停桨来“结束脚本”。需要结束飞行时，使用已经验证的接管与降落流程。

## 13. 3 秒无位移降落保护（2026-10-21）

- **从发布 `/goal` 的墙钟时刻计时**，不是起飞时，也不是看到 CMD_CTRL 时；检查周期约 50ms，调度负载会影响实际延迟，不是硬实时保证。
- 默认 3 秒窗口内最大水平距离 `sqrt((x-x0)^2+(y-y0)^2)` 小于 `0.05m` 则触发；高度变化、速度指令或状态3本身不算移动。
- 可用 `--min-goal-motion 0.05` 明确阈值；允许 0.03~0.10m，且不能超过本次目标水平距离的一半。阈值过小会被定位噪声骗过，过大可能误触发。
- 触发前再次核对新的 EKF/IMU、RC、armed、OFFBOARD 和控制状态；RC切换/拨杆接管、定位超时或掉模式时**不抢飞手、不盲发降落**，报错交给飞手。
- 只发布一次 `TakeoffLand.LAND`，不调用 MAVROS 模式、解锁或停桨服务；2 秒内必须观察到 `AUTO_LAND(5)`，否则报错、不重试。
- **本次也修改了 PX4Ctrl**：旧版 CMD_CTRL 会拒绝 LAND，AUTO_HOVER 也会先接受新轨迹；新版在自动悬停/指令状态中让有效 LAND 优先于规划指令，保留 RC/里程计失效退出。必须在地面锁桨后编译并重启 PX4Ctrl，不能只替换 Python。编译命令见全流程第0节。
- AUTO_LAND 会沿 PX4Ctrl 既有降落逻辑下降，落地判定后可能由 PX4Ctrl 自动停桨；这不是空中强制停桨。执行前必须确认机体正下方可降落。
- 只保护**这个脚本自己发出的目标**的最初 3 秒。手动 RViz/rostopic 发目标、脚本 Ctrl+C/进程崩溃、起飞阶段失败、3 秒后卡死均不在此保护范围内。已有足够位移也不代表朝正确方向移动/到点；定位漂移也可能被当作运动。
- `--takeoff-only` 不发目标，也不启动本保护；不要从已悬停状态重新运行完整起飞流程。
- LAND不会撤销规划器原目标。飞手若取消降落，不要在未清理旧任务时重新拨回指令控制，避免恢复遗留轨迹；落地锁桨后再按文档重置下一轮。

离线脚本测试现为49项，其中新增15项覆盖原地应急指令、没有轨迹、有效位移、定位噪声、仅垂直变化、遥控/模式接管、定位超时、LAND单次发送和拒绝超时。测试通过不代表已经实飞验证。
