# 平地多次端起、放下：高度异常录包分析（2026-11-16）

## 1. 本次已经确认什么

分析对象：`~/gcs_ws/log/z_height_20261116_224924/height.bag`，时长 93.159 秒、约 368.6 MiB；参数快照为同目录 `runtime_all.yaml`。下文时间均为相对录包开始的秒数，Z 为各定位世界系的位置数值，**不是对地高度**。

**平地不同位置放下后，Faster-LIO 自己的 `/Odometry` 已存在约 0.33 m 的静止高度差；ROS EKF、视觉位姿桥、PX4 随后跟随该变化。不是 RViz 回放才生成的误差，也不能只靠修改 PX4 高度源或下游 TF 修好。**

用户描述各放置点均在平地。独立取原始雷达下方大平面拟合，得到六个静止段机体参考点到平面的垂直距离约 0.336～0.344 m，与“各点放置高度基本相同”相符。这加强了上游定位有问题的证据，但不等于有外部真值的完整精度标定。

本包静止段最大差约 0.33 m，**不是对此前 0.8 m 现象的原样复现**；端起期间真实抬升的峰值不能算落地高度误差。当前已定位故障层级，尚未证明唯一的算法或标定根因。

本轮只读原包、做无 ROS master/硬件接口的离线计算并写报告；没有修改正式配置、重启用户定位节点、解锁、切模式或发控制目标。录包中的 94 条 FCU 状态均为 connected=true、armed=false、AUTO.LOITER。

## 4. 本次不能再用 CPU 积压解释

与前一次 22:20 左右的实机采样不同，**这份新包里实时性表现正常，但高度仍异常**：

- `/Odometry` 共 931 条，按 header 间隔约 10.000 Hz，时间戳没有倒退或重复。
- bag 接收时间减 LIO header 时间：中位 47.74 ms、P95 64.41 ms、最大 96.75 ms。
- 18 条 LIO 性能日志中，`pending_lidar` 全为 0；`scan_end_age_s` 最大约 75.6 ms。
- 新包 `/rosout_agg` 没有 WARN/ERROR，也没有前次 `odom time out of buffer time range`。
- 本包没有 CPU/tegrastats 采样，不能凭上述数据宣称当前全机 CPU 低负载；只能说没有观察到此前的持续排队/旧帧问题。

因此，前次“CPU 过载导致 EKF 历史观测超窗”依然是那次真实存在的问题，但**不足以解释这次平地 Z 差**。不要把每次高度异常都归为同一个原因，也不要通过关闭时间检测掩盖它。

## 5. 坐标链和发布者

bag 连接头确认：`/Odometry` 唯一记录发布者为 `/laserMapping`，`/ekf/ekf_odom` 为 `/ekf`，`/mavros/vision_pose/pose` 为 `/ekf_vision_bridge`，PX4 本地里程计为 `/mavros`。没有记录到两套 LIO 同时向 `/Odometry` 发布。

```text
/livox/lidar + /mavros/imu/data_raw
  -> Faster-LIO /Odometry [camera_init]          <-- 此处已经有高度差
  -> ROS EKF /ekf/ekf_odom [world]
  -> /mavros/vision_pose/pose [world]
  -> PX4 /mavros/local_position/odom [map]
```

`/tf` 包含 camera_init→imu/body；`/tf_static` 为 MAVROS 的 map/odom/base_link 与 NED/FRD 配套变换。当前 ROS EKF 直接输出 world，视觉桥复制位姿。这次不是仅由 RViz Fixed Frame 或回放额外旋转造成；但不代表整个 TF 树已经完成独立的外部几何验收。

## 7. 后续排查顺序与安全边界

1. 现有包已足以定位到 Faster-LIO，不需要为“是不是下游 PX4/回放才出错”重复同样录包。先用这份输入做独立 FAST-LIO2 与 Faster-LIO 对照，确认差异是否跟随实现。
2. 优先核查 LIO 地图/点到平面约束、初始化、运动去畸变，以及 IMU/LiDAR 外参和时间偏移是否仍与当前 PX4 IMU 坐标、时钟相符。不能仅凭一份旧标定已通过就排除这些项，也不能只靠本算法自己的姿态反推“最佳偏移”后直接上机。
3. 若需严格复现本次在线结果，下一次应从 LIO 启动前开始录制，含完整初始化；必要时加入雷达自带 IMU和对应飞控 ULog，以区分传感器链路/标定与配准算法。不要直接把雷达 IMU 切成输入却沿用 PX4 IMU 外参。
4. 暂不改 PX4 高度融合、正式 0.05/0.15 参数、航点 Z 补偿，不把 Z 强行锁零。单纯补航点高度或加大碰撞膨胀不能修复定位。
5. 在高度一致性验收前暂停自主起飞测试；继续动力隔离的手持测试。帧率达标不等于定位精度达标。

### 9.1 重要补充：FAST-LIO2 的原始 Z 差主要符合固定坐标倾斜

对原始雷达重复下方平面拟合，六段参考点到平面约 0.3395～0.3479 m。首段地面在 LIO 世界系中的法线为 `[0.02648233, -0.00331912, 0.99964377]`，相对 +Z 倾斜约 **1.53°**；其余段平面倾角约 1.31～1.44°。

只使用首段原始点云确定的固定法线 `n`，计算各静止位置相对首段的 `n · (p - p0)`，没有用后续里程计位置去拟合最佳校正平面。结果如下：

| 诊断量 | FAST-LIO2 本轮 | Faster-LIO 前轮 |
|---|---:|---:|
| 静止位置原始 Z 极差 | 0.1256 m | 0.3324 m |
| 投影到各自首段地面法线后的极差 | 0.0160 m | 0.3236 m |

例如，FAST-LIO2 的 P2 距首段约 4.54 m，Z 增加约 12.56 cm；仅按首段地面倾斜预计就有约 12.01 cm 的 Z 变化。**这支持本轮大部分原始 Z 差是坐标轴与地面不垂直，而非同等大小的累计高度漂移。** 1.6 cm 是离线投影诊断残差，不是外部真值精度，也不是已经向 EKF、地图和控制器应用过修复。

当前 FAST-LIO2 源码 `src/FAST_LIO/src/IMU_Processing.hpp` 的初始化按平均加速度设置重力向量，没有在该段显式将初始姿态旋转到重力对齐系；当前 Faster-LIO 源码则显式旋转初始姿态并令重力为 -Z。源码差异与“不可把两个实现的初始坐标约定当作完全相同”有关，但源码检查不代替对在用二进制的完整构建溯源。

Faster-LIO 旧包用相同的固定法线诊断后仍约 32 cm，**不能靠同样一个固定倾斜补偿解释掉旧包异常**。下一步应分开处理 FAST-LIO2 的水平坐标对齐，以及 Faster-LIO 的初始化/地图约束/去畸变问题；严格 A/B 还需统一输入和参数。若实施坐标对齐，必须一致变换位置、姿态、速度、点云和相关 TF/目标，不能只改 Z 数字或只改 frame_id。

本轮未修改正式参数、切换默认后端、启动飞行或改动 PX4 配置。FAST-LIO2 可先作为后续地面验证的对照基线，但本次手持结果不等于已经通过带动力飞行验证。

新包旁的 `analysis/` 留存 `static_comparison.json/png`、`height_chain.png`、`series.npz`、`summary.json` 和原始平面拟合结果。`static_comparison.png` 两个面板是不同运动，时间轴不能逐点配对；橙线仅为离线法线投影，没有修改线上输出。分析脚本需要可正常读取索引的包：重新运行 `analyze.py` 前，在其目录放置分析副本 `height.bag`，或修改 BAG 路径；恢复索引的包副本仍在 `/tmp`，未将大包再次复制进工作区。
